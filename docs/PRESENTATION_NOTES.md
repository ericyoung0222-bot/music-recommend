## 1. 서비스 소개 (30초)

"저희 서비스 **곡찾기**는 좋아하는 노래를 3~5곡 고르면, 그 곡들과 분위기가 비슷한 노래를 **15곡** 추천해 주는 웹사이트입니다.
국내곡·해외곡, 발라드·힙합·록·재즈·클래식까지 장르와 상관없이 추천이 나오도록 만들었습니다.
마음에 드는 곡은 **플레이리스트**에 담을 수 있고, 곡마다 **별점(1~5점)** 을 남기면 다른 사람들의 평균 별점도 함께 볼 수 있습니다.
낮게 평가한 곡(2점 이하)은 다음 추천부터 자동으로 빠집니다."

주요 기능 4가지:

| 기능 | 설명 | 로그인 필요 |
|---|---|---|
| 추천받기 | 3~5곡 선택 → 비슷한 곡 15곡 | 아니요 |
| 플레이리스트 | 만들기·이름 바꾸기·삭제, 곡 담기·빼기 (최대 200곡) | 예 |
| 별점 | 곡마다 1~5점, 모든 사용자의 평균·인원 표시 | 주기: 예 / 보기: 아니요 |
| 내 평점 | 내가 평가한 곡 목록, 최신순·점수순 정렬 | 예 |

## 3. 구조 (아키텍처)

> 👉 **아키텍처**: 프로그램이 어떤 부품으로 이루어져 있고 서로 어떻게 연결되는지 그린 설계도

```
                ┌──────────────────────────────┐
                │        GitHub Pages          │  ← HTML·CSS·JS 파일을 그대로 올려 두는 무료 웹 호스팅
                │  (ericyoung0222-bot.github.io)│
                └──────────────┬───────────────┘
                               │ ① 사이트 파일 내려받기
                               ▼
┌──────────────┐  ② 곡 검색·비슷한 곡  ┌──────────────────────────────┐
│   Last.fm    │ ◀───────────────────▶ │         사용자 브라우저        │
│     API      │    (JSON 응답)        │  HTML + CSS + JavaScript     │
└──────────────┘                       │  (추천 계산은 여기서 함)       │
                                       └──────────────┬───────────────┘
                                                      │ ③ 구글 로그인
                                                      │ ④ 플레이리스트·별점 저장/읽기
                                                      ▼
                               ┌──────────────────────────────────────┐
                               │               Firebase               │
                               │  Authentication (구글 로그인)          │
                               │  Firestore (데이터베이스 + 보안 규칙)   │
                               └──────────────────────────────────────┘
```

- 👉 **GitHub Pages**: GitHub 저장소의 파일을 웹사이트로 바로 공개해 주는 무료 서비스. 서버 프로그램은 돌릴 수 없고 파일만 보여 줌
- 👉 **API**: 다른 서비스에 "이 데이터 주세요"라고 요청하는 약속된 방법
- 👉 **Last.fm API**: 전 세계 사람들이 들은 음악 기록을 바탕으로 "이 곡과 비슷한 곡", "이 가수와 비슷한 가수"를 알려 주는 무료 API
- 👉 **Firebase**: 구글이 만든 앱 개발 도구 모음. 우리는 로그인(Authentication)과 데이터베이스(Firestore)를 씀
- 👉 **Firestore**: 인터넷에 있는 데이터베이스. 문서(document)를 폴더(collection)에 넣는 구조
- **서버를 따로 만들지 않았습니다.** 브라우저가 Last.fm과 Firebase에 직접 요청하고, 추천 계산도 브라우저 안에서 합니다. 그래서 무료로 운영할 수 있고, 데이터 보호는 Firebase의 **보안 규칙**이 맡습니다(5장).

사용한 기술: 순수 HTML·CSS·JavaScript (👉 **프레임워크 없이**: React 같은 도구 없이 브라우저 기본 기능만 사용), Firebase SDK 13.4.0, Last.fm API, GitHub Pages

## 4. 추천 알고리즘

> 👉 **알고리즘**: 문제를 푸는 순서와 규칙. 여기서는 "입력곡 3~5개 → 추천곡 15개"를 고르는 규칙
> 코드: `js/recommend.js`

### 한 문장 요약

"입력곡마다 비슷한 곡 목록을 받아서, **곡마다 점수를 0~1로 맞춘 뒤 더하고**, 같은 곡·같은 가수가 몰리지 않게 걸러서 **상위 15곡**을 보여 줍니다."

### 단계별 설명

1. **비슷한 곡 가져오기**
   입력곡마다 Last.fm에 "이 곡과 비슷한 곡 50개"를 요청합니다(`track.getSimilar`). 각 곡에는 0~1 사이 **유사도 점수(match)** 가 붙어 옵니다.

2. **곡마다 보충 (국내곡 대응)**
   비슷한 곡이 **10개 미만**인 입력곡은 따로 보충합니다.
   - 그 가수의 인기곡 3곡 + 비슷한 가수 5명의 인기곡 3곡씩
   - 보충곡 점수 = 가수 유사도 × **0.3** (진짜 "비슷한 곡"보다 낮게 줌)
   - 이유: 국내곡은 Last.fm에 기록이 적어서 "비슷한 곡"이 0개인 경우가 많았습니다.

3. **곡마다 점수 맞추기 (0~1 정규화)**
   👉 **정규화**: 서로 기준이 다른 점수를 같은 범위로 맞추는 것
   입력곡마다 가장 높은 점수가 1이 되도록 나눕니다. 이렇게 안 하면 정보가 많은 해외곡 하나가 결과를 거의 다 차지합니다.

4. **합산**
   여러 입력곡에서 함께 나온 곡은 점수를 더합니다. 그래서 **여러 입력곡과 동시에 비슷한 곡**이 위로 올라옵니다.

5. **빼야 할 곡 빼기**
   - 입력곡 자신, 그리고 **같은 가수**가 올린 **같은 곡의 다른 표기**(예: "우주를 줄게"를 골랐을 때 "Galaxy 우주를 줄게")
   - 로그인했다면 **내가 2점 이하로 준 곡**

6. **정렬하고 고르기**
   점수가 높은 순(같으면 여러 입력곡에서 나온 순)으로 정렬한 뒤
   - 제목이 사실상 같은 곡(괄호·feat. 표기만 다른 곡)은 하나만
   - **같은 가수는 최대 2곡**
   - 상위 **15곡**

7. **그래도 5곡 미만이면** 모든 입력곡 가수의 비슷한 가수 인기곡으로 한 번 더 보충합니다.

8. **앨범 이미지 채우기**: 이미지가 없는 곡은 `track.getInfo`로 한 번 더 찾아봅니다.

### 속도와 예의

- 👉 **동시 요청 3개 제한**: Last.fm 서버에 한꺼번에 너무 많이 요청하지 않도록 동시에 3개씩만 보냄
- 👉 **캐시(cache)**: 한 번 받은 결과를 브라우저에 잠깐 저장해서, 같은 요청은 다시 보내지 않음 (`sessionStorage`, 탭을 닫으면 사라짐)

### 예시로 설명하기 (말로)

"아이유 '밤편지'는 Last.fm에 비슷한 곡 정보가 거의 없습니다. 그래서 아이유와 비슷한 가수들의 인기곡을 점수를 낮춰서 후보로 넣습니다. Coldplay 'Yellow'는 비슷한 곡이 50개 다 나옵니다. 두 곡의 점수를 각각 0~1로 맞춘 다음 더하기 때문에, 정보량 차이와 상관없이 두 곡의 영향이 비슷하게 반영됩니다."

## 5. 데이터 구조와 보안

### 데이터 구조 (Firestore)

```
users/{uid}                          사용자 정보 { 이름, 프로필 사진, 가입 시각 }
users/{uid}/playlists/{id}           플레이리스트 { 이름, 만든 시각, 바꾼 시각, 곡 목록[] }
users/{uid}/ratings/{곡키}            내 별점 { 점수, 곡 제목, 가수, 이미지, 링크, 시각 }
tracks/{곡키}/ratings/{uid}           곡별 별점 { 점수, 시각 }   ← 평균 계산용, 누구나 읽기
```

- 👉 **uid**: 구글 로그인하면 Firebase가 사람마다 붙여 주는 무작위 ID
- 👉 **곡 키**: "가수::제목"을 소문자로 바꿔 합친 것. 플레이리스트 중복 확인, 별점 문서 이름, 추천 중복 제거에 모두 이 하나만 씀
- 별점은 **두 곳에 한 번에** 저장합니다(👉 **batch**: 여러 저장을 묶어서 전부 성공하거나 전부 실패하게 하는 기능). 평균과 인원수는 Firestore의 👉 **집계 쿼리**(문서를 다 내려받지 않고 서버에서 평균·개수만 계산)로 구합니다.

### 보안 (자세한 내용: [SECURITY.md](SECURITY.md))

> 👉 **보안 규칙**: Firebase 서버가 모든 읽기/쓰기마다 검사하는 조건. 브라우저 코드를 고쳐도 피할 수 없음

| 데이터 | 읽기 | 쓰기 |
|---|---|---|
| 사용자 정보 | 본인만 | 처음 로그인할 때 한 번만 |
| 플레이리스트 | 본인만 | 본인만. 이름 1~50자, 곡 200개 이하, 정해진 항목만 |
| 내 별점 | 본인만 | 본인만. 점수는 1~5 정수만 |
| 곡별 별점 | 누구나 (평균 표시) | 내 uid 문서에만, 점수 1~5 정수 |
| 그 밖 | 거부 | 거부 |

그 밖의 조치:
- 👉 **XSS 방어**: 곡 제목 등은 모두 "글자"로만 화면에 넣어서, 이상한 코드가 들어 있어도 실행되지 않음
- 👉 **CSP**: "이 사이트는 정해진 곳의 스크립트·이미지만 쓴다"고 브라우저에 알려 주는 설정
- 👉 **API 키 리퍼러 제한**: Firebase 키를 우리 사이트 주소에서만 쓸 수 있게 제한
- **자동 테스트 49개**: 👉 **에뮬레이터**(실제 DB 대신 내 컴퓨터에서 돌리는 가짜 Firebase)로 "남의 플레이리스트 읽기", "별점 6점 넣기" 같은 공격 32개가 모두 막히는 것을 확인

남은 한계(질문 나오면): Last.fm 키는 정적 사이트라 공개될 수밖에 없음(과제 후 폐기), 곡별 별점은 평균을 보여 주려고 공개 읽기라 uid와 점수가 보임(uid는 무작위 문자열이라 이름·이메일과 바로 연결되지 않음).

| **국내곡은 추천이 거의 안 나옴** | Last.fm은 해외 사용자 중심이라 국내곡의 "비슷한 곡" 정보가 0개인 경우가 많음 | 비슷한 곡이 10개 미만인 입력곡만 **가수 기반으로 보충**하고, **곡마다 점수를 0~1로 맞춰** 해외곡이 결과를 독차지하지 않게 함. 그 결과 발라드·인디·아이돌·트로트·힙합·록·팝·재즈·클래식·J-pop·혼합 모두 15곡 확인 |
| 추천에 입력곡이 다른 표기로 또 나옴 / 반대로 상관없는 곡이 빠짐 | "Galaxy 우주를 줄게"처럼 같은 곡이 다른 제목으로 등록됨. 처음엔 제목만 비교해서 "사랑"을 고르면 다른 가수의 "첫사랑"까지 빠짐 | **가수가 같을 때만** 다른 표기를 같은 곡으로 판단 |
| "곡 제목 가수"로 검색하면 못 찾음 | Last.fm 검색은 제목만 넣어야 잘 찾음 | 검색어 앞/뒤 1~2단어를 가수로 가정해 여러 번 검색 → 제목·가수가 검색어에 들어 있는 곡과 청취자 많은 곡을 위로 |
| **휴대폰에서 검색 후보를 눌러도 선택이 안 됨 (1)** | 입력창에서 손을 떼는 순간(blur) 목록을 닫게 했는데, 터치에서는 이 일이 "누름(click)"보다 먼저 일어나 누를 대상이 사라짐 | blur 대신 "검색 영역 **바깥**을 눌렀을 때"만 닫도록 변경, 터치 후에는 키보드가 다시 올라오지 않게 함 |
| **휴대폰에서 검색 후보를 눌러도 선택이 안 됨 (2)** | 폰에서 한글을 칠 때 마지막 글자가 "조합 중"인데, 후보를 누르는 순간 그 글자가 확정되며 검색이 한 번 더 예약됨 → 0.3초 뒤 목록이 다시 열려 고른 곡을 덮음 | 후보를 고르면 예약된 검색을 취소하고, 검색어가 바뀐 뒤 늦게 온 결과는 버림 |
| 새 플레이리스트를 만들며 곡을 담을 때 빈 플레이리스트만 남을 수 있음 | "만들기"와 "곡 담기"를 두 번에 나눠 저장해서, 두 번째 저장이 실패하면 빈 플레이리스트만 남음 | **한 번의 저장**으로 합침 |
| 보안 규칙이 너무 느슨함 / 너무 빡빡하면 기능이 막힘 | 규칙은 정확히 정해진 항목만 허용해야 안전하지만, 코드가 보내는 항목과 한 글자라도 다르면 저장 실패 | 코드의 모든 저장 기능과 규칙을 **표로 하나씩 대조**하고, 에뮬레이터로 허용 17개·거부 32개를 자동 테스트 |
| 앨범 이미지가 회색 별로 나옴 | Last.fm이 이미지가 없을 때 회색 별 그림을 줌 | 그 그림은 "이미지 없음"으로 보고 다른 방법으로 다시 찾거나 기본 이미지 표시 |

### 디자인과 기능을 나눈 방법 (`data-js`와 `class` 분리)

"세 명이 같은 HTML을 동시에 고치면 서로 망가뜨리기 쉽습니다. 그래서 **역할마다 다른 이름표**를 쓰기로 했습니다."

```html
<button class="btn btn--primary" data-js="recommend-submit">추천받기</button>
```

- `class="btn btn--primary"` → **디자인용**. 디자인 담당이 마음대로 바꿔도 됨
- `data-js="recommend-submit"` → **기능용**. JavaScript는 이 이름으로만 요소를 찾음. 디자인 담당은 건드리지 않음
- 상태(로딩 중, 선택됨 등)는 JS가 `is-loading`, `is-active` 같은 `is-*` 클래스만 붙였다 뗌 → 모양은 CSS가 결정
- JS 안에 스타일을 직접 쓰지 않음(인라인 스타일 0개)
- 반복되는 부품(곡 카드, 별점 등)은 `partials/templates.html`에 한 번만 만들어 두고 JS가 복사해 씀
- 👉 **styleguide.html**: 모든 부품을 가짜 데이터로 한 화면에 보여 주는 페이지. 디자인 담당은 로그인이나 API 키 없이 여기서 모양을 확인

**효과**: 디자인 담당이 class를 아무리 바꿔도 기능이 깨지지 않고, 개발자가 기능을 고쳐도 디자인이 깨지지 않습니다.

## 8. 예상 질문과 답변

**Q1. 추천은 AI(머신러닝)인가요?**
A. 직접 학습시킨 AI는 아닙니다. Last.fm이 전 세계 사용자의 감상 기록으로 계산한 "비슷한 곡·비슷한 가수" 정보를 받아서, 저희가 만든 규칙(점수 맞추기, 합산, 중복·가수 제한, 보충)으로 15곡을 고릅니다. 많은 사람의 감상 기록을 바탕으로 한 **협업 필터링** 결과를 활용한다고 볼 수 있습니다. (👉 협업 필터링: "이 곡을 들은 사람들이 많이 들은 다른 곡"을 찾는 방식)

**Q2. 왜 Spotify나 멜론이 아니라 Last.fm인가요?**
A. Spotify는 2024년 11월부터 새로 만든 앱에서 추천·비슷한 가수 기능을 쓸 수 없게 막았고, 멜론 등 국내 서비스는 공개 API가 없습니다. Last.fm은 무료로 "비슷한 곡" 정보를 주는 거의 유일한 API였습니다.

**Q3. 국내곡은 Last.fm 데이터가 적다는데, 어떻게 추천이 나오나요?**
A. 비슷한 곡 정보가 10개 미만인 곡만 골라서, 그 가수의 인기곡과 비슷한 가수의 인기곡으로 보충합니다. 대신 점수를 0.3배로 낮춰서 진짜 "비슷한 곡"보다 앞에 오지 않게 했습니다. 그리고 입력곡마다 점수를 0~1로 맞춰서 해외곡과 섞어도 한쪽이 결과를 독차지하지 않습니다.

**Q4. 같은 가수 노래만 잔뜩 나오지 않나요?**
A. 같은 가수는 최대 2곡으로 제한했습니다. 또 제목이 괄호나 feat. 표기만 다른 같은 곡은 하나만 보여 줍니다.

**Q5. 별점은 추천에 어떻게 쓰이나요?**
A. 로그인한 상태에서 2점 이하로 준 곡은 다음 추천에서 빠집니다. 다른 사람들의 평균 별점은 카드에 표시만 하고, 추천 순위에는 쓰지 않습니다.

**Q6. 서버 없이 만들었다는데, 데이터는 안전한가요?**
A. 데이터는 Firebase의 보안 규칙이 서버에서 지킵니다. 브라우저 코드를 고쳐도 남의 플레이리스트를 읽거나 별점을 6점으로 넣을 수 없습니다. 이걸 에뮬레이터로 공격 32가지를 시도해서 모두 막히는 것을 확인했습니다.

**Q7. API 키가 코드에 그대로 보이는데 괜찮나요?**
A. Firebase 키는 원래 공개되는 값이고, 우리 사이트 주소에서만 쓸 수 있게 제한했습니다. Last.fm 키는 공개 정보 조회만 가능한 과제용 키라서, 과제가 끝나면 폐기합니다. 서버가 없는 정적 사이트의 한계라 문서에도 적어 두었습니다.

**Q8. 다른 사람이 내 별점을 볼 수 있나요?**
A. 평균을 보여 주려고 곡별 별점은 누구나 읽을 수 있게 했습니다. 다만 거기에는 무작위 ID(uid)와 점수만 있고, 이름·이메일은 본인만 읽을 수 있는 곳에 따로 있어서 누가 줬는지 바로 알 수는 없습니다.

**Q9. 휴대폰에서도 되나요?**
A. 됩니다. 휴대폰 터치에서 검색 후보가 선택되지 않는 문제를 찾아서 고쳤고(6장), 버튼과 후보는 손가락으로 누르기 쉬운 크기(44px 이상)로 만들었습니다. 화면 배치는 디자인 담당이 모바일 반응형을 맡았습니다.

**Q10. 세 명이 같은 파일을 고치면 충돌나지 않나요?**
A. 역할별로 이름표를 나눴습니다. 디자인은 `class`, 기능은 `data-js`만 쓰기 때문에 디자인 담당이 class를 바꿔도 기능이 깨지지 않습니다. 작업은 이슈로 나누고, 각자 브랜치에서 작업한 뒤 PR로 확인받고 합칩니다.
